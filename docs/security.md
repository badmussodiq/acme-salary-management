# Security review

Salary data is sensitive, so this document records what protects it, how each control is proven, what the Phase 5 review changed, and which risks are knowingly accepted.

## Controls and the tests that prove them

| Threat                               | Control                                                                                                                                                                                                                                                                      | Proof                                                                                                                                                       |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SQL injection                        | Kysely with bound parameters only. Sort fields, group-by and filters come from closed enums. `LIKE` input is escaped. The two raw fragments are fixed constants from an allowlist                                                                                            | Injection strings in search, filters, names and login; `escapeLike` unit tests; `employees`, `insights` and `security` integration specs                    |
| Invalid or hostile input             | Global `ValidationPipe` with whitelist and `forbidNonWhitelisted`; every string has a length and pattern, every number a range, every enum a closed set; JSON parser rejects `__proto__`, `constructor`, `prototype`; only `application/json` is parsed                      | `validators`, `validation.pipe`, `configure-app` unit tests; prototype-pollution, malformed JSON, form-encoded and plain-text bodies in `security.int-spec` |
| Brute force and credential stuffing  | scrypt (N=2^15, r=8, p=3); uniform error and constant-time work for unknown users; 5 failures lock the account for 15 minutes; login limited to 5 per minute per address                                                                                                     | `auth.units.spec`, `auth.int-spec` (lockout and 429)                                                                                                        |
| Stolen or stale session              | HttpOnly, SameSite=Strict, Secure (production) cookie; signed JWT with a per-user session version, so **sign-out revokes every session of that user server-side**; disabled users rejected on every request                                                                  | `security.int-spec` (revocation, other devices, Secure flag), `auth.spec` (cookie hidden from scripts, revoked session returns to sign-in)                  |
| Account recovery and password change | Reset link is a signed JWT with its own audience, 30-minute expiry and a fingerprint of the current password hash, so it works once; the request answers 202 for any email; reset and change revoke other sessions; change needs the current password; both are rate-limited | `auth.int-spec` (password reset, change-password)                                                                                                           |
| Broken access control                | Deny-by-default global auth guard, roles guard, origin guard on state-changing requests                                                                                                                                                                                      | Table-driven 401 test over every business route; 403 for foreign origin; roles guard unit tests                                                             |
| CSRF                                 | SameSite=Strict cookie plus a rejected foreign `Origin`                                                                                                                                                                                                                      | `auth.int-spec`                                                                                                                                             |
| XSS and clickjacking                 | Nonce-based CSP with `strict-dynamic` (no `unsafe-eval` in production), `frame-ancestors 'none'`, `X-Frame-Options`, no raw HTML rendering, React escaping                                                                                                                   | `csp.spec`; browser tests assert the header and that pages render with zero CSP violations                                                                  |
| Denial of service                    | Per-user (signed in) or per-address rate limits; 100 KB body cap on the API **and** on the web proxy; page-size cap; API header (15 s) and request (30 s) timeouts; 20 s upstream timeout in the proxy; database statement timeout and pool cap                              | `platform.e2e-spec`, `security.int-spec` (per-user limit, 413, timeouts), `body-limit.spec`                                                                 |
| Data exposure                        | Generic 500s; no stack traces or submitted values in errors; `Cache-Control: no-store` on every API response; logs carry ids and request ids, never email, salary or tokens                                                                                                  | `security.int-spec`, `platform.e2e-spec`                                                                                                                    |
| Mass assignment                      | DTO whitelisting; explicit mapping to table columns; response DTOs only                                                                                                                                                                                                      | `employees.int-spec` (unknown fields rejected)                                                                                                              |
| Lost updates and audit tampering     | Optimistic version on employees; row lock when changing pay; database trigger makes `audit_events` append-only                                                                                                                                                               | `employees.int-spec`, append-only test                                                                                                                      |
| Vulnerable dependencies and secrets  | `pnpm audit` gates CI; Dependabot (npm, Actions, Docker); full-history gitleaks scan in CI; Trivy gates every image before it is pushed                                                                                                                                      | CI and CD workflows; both scans were clean when run for this review                                                                                         |
| Container breakout and privilege use | Minimal Alpine runtime, unprivileged user, read-only root filesystem, all capabilities dropped, `no-new-privileges`, PID limit, init process, API not published to the host                                                                                                  | Browser suite passes against the hardened containers; `scripts/probe-security.sh`                                                                           |

`scripts/probe-security.sh [base-url]` probes a running stack for the headers, the proxy body cap, the 401 envelope, hostile bodies and an unexposed API port.

## What the Phase 5 review found and fixed

| Finding                                                                                                        | Fix                                                                                          |
| -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Signing out only cleared the cookie; a stolen token stayed valid for 8 hours                                   | Per-user session version in the token; sign-out bumps it                                     |
| Write limits were per address, not per user as designed                                                        | Throttler tracks the signed-in user, falling back to the address                             |
| No Content-Security-Policy on the web app                                                                      | Per-request nonce CSP from the proxy; all pages render dynamically so every script is nonced |
| The web proxy buffered any request body and had no timeouts                                                    | 100 KB streaming cap and a 20 s upstream timeout; 15 s timeout on server-side fetches        |
| API accepted `application/x-www-form-urlencoded`                                                               | Parser removed; only JSON is read                                                            |
| `__proto__` keys were silently ignored rather than rejected                                                    | JSON reviver rejects them with a 400                                                         |
| A production deployment could silently run with the development JWT secret                                     | Startup fails if the production secret equals the development default                        |
| API responses could be cached by browsers or intermediaries                                                    | `Cache-Control: no-store`                                                                    |
| No slow-client protection on the API server                                                                    | Header and request timeouts                                                                  |
| Containers ran with default privileges                                                                         | Read-only, no capabilities, no-new-privileges, PID limit                                     |
| No automated dependency, secret or image review                                                                | Dependabot, gitleaks and Trivy in the pipelines                                              |
| **A revoked or expired session looped forever between sign-in and the dashboard** (found by the browser tests) | `/session-expired` clears the stale cookie, then goes to sign-in                             |
| The first version of that fix redirected to `0.0.0.0` inside the container (found by the container test run)   | Relative redirect                                                                            |

## Accepted risks and limits

- **One role and no per-employee scoping.** Every HR manager can see every salary. Fine for the single persona in the brief; finer roles would add a column and a guard, not a redesign.
- **Account lockout can be used to lock the HR manager out.** The per-address login limit slows an attacker, but a determined one can still trigger a 15-minute lock. The alternative (no lockout) is worse for a salary system.
- **Sign-out everywhere.** One counter per user means signing out on one device ends every session. Per-session records would allow finer control.
- **The API connects as the database owner**, because it runs its own migrations at start-up. A separate migration role with a restricted runtime role is the next step.
- **The updater mounts the Docker socket**, which is root-equivalent on the host. Mitigate with a socket proxy, or switch to a pull-based deployment from CI, if the host also runs other workloads.
- **The rate-limit store is in memory.** Each replica counts separately and counters reset on restart. A shared Redis store is needed before running several API replicas.
- **`style-src` allows inline styles** (React style attributes for chart widths and Next's own styles). Scripts, the higher-risk surface, are strictly nonced.
- **No MFA, password change or password reset.** The first HR manager is created from configuration; user management is out of scope for the assessment.
- **Seeded records have no human actor.** Their audit events are attributed to the system and flagged as synthetic.
- **Client addresses depend on the proxy chain.** The API trusts one proxy hop (`TRUST_PROXY_HOPS=1`): Caddy sets the client address and the web app forwards it. Deploying behind a different chain needs that value revisited, or per-address limits become spoofable.
